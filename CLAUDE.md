# Gunsmith3D: read this first

## The vision

Gunsmith3D is a firearm design sandbox, with a career mode to come later. The designer is a **blank workshop, not a catalogue of gun types**.

- **Anything a player can imagine should be buildable**, however impractical or "cursed": a shotgun-shell pistol, a bolt-action machine gun, a revolver with three barrels. If it can be drawn, it should be possible.
- **The game never decides what a gun "is".** The only classification is **one-handed or two-handed**. How a gun feeds, locks, fires and handles comes entirely from the parts the player made.
- **Usefulness is the player's problem.** Bad designs are allowed. They just perform badly: they kick hard, jam, or are unwieldy. Never block a design for being impractical.
- **Examples are inspiration, not templates.** The example guns (blowback pistol, tilting barrel, bolt action...) show what's possible and should be polished. But nothing in the code may be special-cased around them, and no feature should assume they're the kinds of firearm that exist.

An earlier version of this project was built as if the examples were the only kinds of gun. That was a misunderstanding of the intent. Don't repeat it.

## Design principles

- **Simulate physical primitives, never gun types.** Mechanisms should emerge from parts, joints, springs, contacts, pressure and cartridges, not from code for "a revolver" or "a pump action".
- **What players must design vs. what can be abstracted** (the owner's rule):
  - Always real, designed parts: **feeding, the bolt and breech, and extraction**.
  - Optional abstraction, with an advanced drawn alternative: **fire control** (trigger, hammer or striker, sear, disconnector). Built-in fire control still has to be cocked by the action.
  - Fine detail that's tiny, hidden or fiddly to draw (feed lips, magazine springs) becomes **settings with good defaults that have real consequences** in the physics. Don't add a setting that does nothing: measure its effect first, and if it has none, leave it out and say so.
- **Unreliable designs jam for real.** On the bench through the physics, and later in live fire by rolling against the gun's measured jam rate. Clearing a jam means running the action.

## Known assumptions still to remove

These are what currently lock the designer. They are the roadmap, roughly in this order:

1. **Several chambers.** Done: `BreechDef::more` (further chambers, each with its own breech part, chamber part, face and muzzle) and `fireOrder` (turn or together). In the simulation, chamber 0's state lives in Sim's usual fields and `useChamber(S, k)` swaps another in (`Sim::chambers`); rounds carry `slot`. The over-under derringer example (hinged, tips up). Still to do: pepperboxes (each chamber its own barrel), a magazine feeding a chamber other than the first, a drawn striker per chamber, a drawn crane/swing-out.

Force at the piston's centre, reaction on the chamber part. A spring on the piston's assembly counts as `breechSprung`. ## Technical notes

- C++17, CMake. Layers: `src/core` (physics, designs, cartridges, reliability, maps; no graphics) → `src/app` (raylib rendering, editor, bench) → `src/ui` (Dear ImGui panels) → `src/main.cpp`. See README "Source layout".
- Headless core and tests: `cmake -S . -B build && cmake --build build -j && ./build/gunsmith3d_tests`
- Native Linux app for screenshots (developer only): `-DGUNSMITH_NATIVE_APP=ON`, then run under `xvfb-run` with `LIBGL_ALWAYS_SOFTWARE=1`. `--frames N --shot file.png` takes a screenshot (saved in the working directory). See `src/main.cpp` for `--preset`, `--select`, `--test`, `--fire`, `--side`, `--tutorial N`, `--mapedit`, and the `GUNSMITH_TAB` variable.
- Windows build from Linux: MinGW-w64 (`g++-mingw-w64-x86-64-posix` from apt) with a toolchain file setting `CMAKE_SYSTEM_NAME Windows` and the `x86_64-w64-mingw32-*-posix` compilers. The project's `cmake-mingw-toolchain.cmake` expects llvm-mingw instead.
- Example guns live in `src/core/presets.inc`, generated by `tools/make_presets.py`. Edit the script, not the .inc.
- Player files (`app/paths.cpp`): the app folder is Documents/OAB Foundry/Gunsmith (`initAppFolder`: settings.json, autosave.json, Crashes; falls back to the game folder), the user folder defaults to its `User` (`defaultUserFolder`, or `Settings::userDir` from Settings > Files, `changeUserFolder` copies files over) with Blueprints, Levels, Textures, Parts, NPCs, Rounds (one JSON per cartridge, `setUserCartridgesDir`), Groups, Characters/character.json. The path globals (`BLUEPRINTS_DIR`, `MAPS_DIR`...) are re-pointed by `setUserFolder`; `setupUserFolders` moves files from the old `user/...`, `blueprints/`, `maps/` folders. Animations stay inside blueprints. Textures: `app/usertex.cpp`; the Windows file box and folder picker are in `app/sysfiles.cpp` (kept apart from raylib because of windows.h name clashes). Map materials named `user:<file>` are the player's pictures. F11 (`Act::Fullscreen`, `toggleFullscreenKey`) toggles windowed and `Settings::lastFullMode`; borderless clears raylib's topmost flag.
- Units (the owner chose: not in Settings, switched on the fly): `unitsSwitch` (ui/common.cpp, mm | in on the designer/bench and level editor toolbars) flips `CFG.units`. `parseQ` (app/units.cpp) reads typed values in either system with fractions and sums (mm, cm, m, in, \", thou, ft, g, kg, gr, oz, lb, m/s, ft/s...); `typedQ` writes them back (exact 32nds of an inch as fractions); `fracInch` is the nearest 32nd. `numFieldU` drags with the mouse and, on a click, turns into a text box read by `parseQ`. Snap: `snapControls` in toolbar.cpp (magnet = `A.snapOn`/`CFG.snapOn`, typed step `gSnap`/`CFG.snap`). Measure: `A.measureKeep` keeps the line drawn with other tools (`measureToolPanel`).
- Sounds: the owner's recordings in `assets/sounds` (pistol_* Thunder .380, rifle_* AR-15, action_* the Thunder's slide, crack_* the opening of AR-15 shots), cleaned and embedded as OGG by `tools/embed_sounds.py` into `app/builtin_sounds.inc`. `core/shotsound.cpp`: `shotMix` (energy blend pistol 300 J -> rifle 1500 J, pitch (E/ref)^-0.2 against each set's own cartridge, blast = J per mm of barrel against the recordings', crack layered for supersonic pistol rounds), `actionMix` (assembly mass, speed). `app/audio.cpp`: `playShot(design, chamber)`, `playShotMix`, `playAction(actionMass(S))`, voice pools with aliases (`LoadSoundAlias`) and +-3% pitch. Hybrid (0.4.14): pistol recordings are only their first 0.12 s (a brass catcher clangs later), rifle ones 0.3 s (voices in the tails), all shots compressed and soft-clipped; `synthBoom`/`synthTail` (core) add a thump (`boomGain/Pitch`, grows with energy) and a range echo (`tailGain/Pitch`, mostly for the pistol side). Clicks (dry fire, magazine) are still synthesised; more recordings to come from the owner (Mauser bolt, AR-15 handling).
- Names (the owner's): the studio is **OAB Foundry** (splash: the owner's logo, `assets/logo/oab_foundry.jpg`, embedded by `tools/embed_logo.py`; the .exe's company name); the developer is **The One Armed Bandit** (the EULA, copyright).
- Launch: `src/ui/intro.cpp` shows the studio splash, then the EULA until it's agreed to once (`Settings::eulaAgreed` keeps a fingerprint of the agreed text; the owner chose: never asked again once agreed, even if the text changes). The EULA text is `src/ui/eula.inc` (a raw string): to drop in the owner's agreement, replace the text there. The owner chose: the agreement lives only inside the game (no EULA.txt in the zip: a text file could be edited); it can be read again from About (`agreementText`). - Releases and updates (0.6.2): `.github/workflows/release.yml` publishes a GitHub release (tag `v<version>-<stage>`, the Windows zip built with MinGW on Linux via `cmake/mingw-gcc.cmake`, notes = the changelog's newest section) whenever a push changes CMakeLists.txt to a version that has no release yet. So shipping = bump the version and push. The zip holds the exe, README, CHANGELOG, BACKLOG, `licenses/` and `dist/user` (sample guns, maps, textures). The game updates itself (`app/updater.cpp`, Windows only; `CFG.autoUpdate`, Settings > Interface): at start a thread asks `api.github.com/repos/<update::REPO>/releases/latest` (WinHTTP), and if the tag is newer (`update::newer`, numbers only) downloads the zip, unpacks it in-process (`unzipTo`, raylib's `DecompressData`), renames the running exe to `.old.exe` and copies the new files over the game folder (the `user/` folder only gets missing files); `update::cleanup` deletes the old exe at the next start; the main menu shows the state and Restart now. The owner made the code repository public, so releases are published there (the workflow uses its own repository unless the secret `RELEASES_TOKEN` is set, which sends them to `LusciousLuchs/Gunsmith3D-Releases`). The updater asks both (`update::REPO`, `update::CODE_REPO`) and takes the newest; `update::checkNow` (Check for updates on the main menu and in Settings) asks again. Test env: `GUNSMITH_UPDATE_API` (another URL; also runs in screenshot runs), `GUNSMITH_NO_UPDATE`. The "What's new" changelog is embedded as a byte array (MSVC refuses string literals over 64 KB).
- Blueprints are JSON. Older blueprints must keep loading and behaving the same: give new fields defaults that reproduce the old behaviour.

- Privacy: never put the owner's file names, place names or any personal detail from their uploads into the repository, commit messages, changelog or release notes (the repository is public). Describe recordings by what they are.
